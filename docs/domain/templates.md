# Templates, hubs and machine Tools

Part of the OpenGroow glossary: see [GLOSSARY.md](../../GLOSSARY.md) for the vision, bounded contexts and term index.

### Hub

A repository that distributes Agent Templates and machine-side tools, with a fixed layout: `index.json` (the catalogue: id, version, sha256 of the release `.tgz`, trust level), `packages/<name>/` (one Agent Template per folder, with its own OpenClaw plugins) and `tools/<name>/` (machine-side tools an Agent invokes through `exec` on a paired node, never installed by the Template itself). A release is a tag `<name>@<version>`: a workflow builds the `.tgz`, attaches it to the release and updates the index (ADR-060). `hub-template/` in the product repository is the skeleton both hubs are created from.

- **`groowhub`**: the public hub (MIT). Anyone can install from it, unauthenticated. Its first Template is `@opengroow/source`; others are published when generic enough (criterion: could someone else run it with their own MCP?).
- **`private-groowhub`**: the private staging hub, same layout. Templates and tools that are not yet generic live here and are installed from a local clone (`pnpm template:add <folder>`), because the installer downloads without authentication. A Template reaches `groowhub` by being published there; the product never reads `private-groowhub`.
- **`tools/`**: machine-side tools (for example the Android CLI) live in a hub, not in the product. The product holds no tool code.
- _Avoid_: "registry" (the per-Project installed set is the Template registry, distinct from the hub), "store", "marketplace". ClawHub is a future second distribution channel for the same packages, not a hub (ADR-060).

### Deployment

The product is the same code in self-host and in the hosted offer. Only the branch behind `InstanceProvisioner` differs: `openclaw-local-control` drives Docker Compose, or a remote control plane implementing `docs/CONTROL_PLANE.md` creates servers (one generic HMAC-signed client, selected by configuration).

- **Two-backend principle**: the hosted offer is a separate private service with its own backend (accounts, subscriptions, quota, fleet). It reaches the product only through signed APIs; the product holds no code of it. Merging the two backends later stays possible; a mixed Convex could not be split (ADR-061).
- **One dashboard**: the same Next.js dashboard serves both; no separate landing, no capability system until the two actually diverge (ADR-062).
- **Self-host authentication**: email and password, single account by default, locked after the first account (ADR-029, ADR-059, ADR-062).

### Agent Template

Reusable blueprint defining the capabilities, available MCP tools, and instructions of an Agent type. Templates are versioned packages distributed by a Hub (see Hub); `packages/agent-templates` holds the engine that reads them, not the Templates.

- An Agent Template is always **versioned and carries an origin** (built-in, hub, or direct URL) and an integrity digest. There is no separate "package" concept in the domain: the distributable form of a Template is the Template itself. Every Agent, including system-like ones such as the Source Agent, is described by the same Template format; what distinguishes a first-party Template from a third-party one is its **trust level** in the catalogue, not a different format.
- **Trust level** (the `verification` field of a hub index entry): `official` (published by the product's maintainers under the reserved `@opengroow` scope), `verified` (a third-party Template reviewed by the maintainers), `community` (unreviewed). The index parser rejects a `verified` or `community` entry that claims the `@opengroow` scope. A trust level is a label shown in the catalogue (Official, Verified, Community), not a permission: every install is checked against the hub's sha256 whatever its level.
- **Official** means two things only: the id is in the `@opengroow` scope, and the package is published from the public hub. The hosted offer lists official, public Templates only (ADR-061).
- A Template id is **scoped**: `@scope/name` (`@opengroow/seo`, `@alice/shopify-seo`). Official Templates live in the `@opengroow` scope (the former pre-launch official scope is deprecated: refused on install, still read from what was stored before the move, #708); the stored ids on Agents, Missions, Schedules, Runs, Sources and Jobs are scoped too. The OpenClaw agent id is derived from the Template id by a slug (`@opengroow/seo` becomes `opengroow--seo`), never the raw id: an Agent keeps the OpenClaw agent it was registered under (`projectAgents.openclawAgentName`) until its next refresh registers the derived one on the same workspace.
- An Agent Template produces Agents when activated within a Project.
- A Template package is a **native OpenClaw Claw** (`openclaw claws add` accepts it as is; a guard test dry-runs the fixtures). Identity: the Template id is the `package.json` name, the Template name and description are the native `agent.name` / `agent.description`, and `agent.id` is the OpenClaw slug of the Template id. Required skills are native `packages` with an exact ClawHub `ref` and `version`. Everything OpenGroow-specific (including the exec node, which OpenClaw's native profile cannot carry) lives in `profiles/opengroow.yml`; the tool deny list is the native `profiles/openclaw.yml`.
- An Agent Template carries the **review contract** for the Artifacts it produces: deliverable type, content to present, and available business actions. A Mission's `type` describes the user's intention; the Template describes how OpenGroow reviews the deliverable.
- **Mission-type contracts are explicit**: when a Template offers several Mission types, each Mission type that produces a reviewable Artifact declares its own review contract. There is no implicit Template-wide review contract that silently applies to an unlisted Mission type.
- An Agent Template can declare **selectable Mission types** (`missionTypes`): each entry carries a `type` (key interpreted by the agent), a `label` (shown in the creation form's `<select>`), and a `payload` (default JSON pre-filled in the creation form). This field is optional: a Template without `missionTypes` leaves a free-text field in the forms. The "Create Mission" and "Create Schedule" dashboards read these types directly from the manifest — there is no static list in the dashboard.
- **Agent / Mission type / Config / Payload separation rule**: four distinct levels, each with a precise role.
  - **Agent** = a capability (producing videos, writing articles). An Agent has a strong, stable objective.
  - **Mission type** = a **qualitatively different** result (format, nature of the deliverable — e.g. a letter video vs a marketing video). Creating a Mission type for each Instagram account would be a violation: the type describes the *what*, not the *where*.
  - **Config** = parameters that are **stable at the Project level** (which publishing account, which channel, which language). Config rarely changes; it is shared across all Missions of the same Agent.
  - **Payload** = **per-run** brief, filled in by the operator when creating the Mission (e.g. `theme`, `platforms`). The Payload is fixed at Mission creation; it carries what is specific to this precise intention, not to all runs of the Agent.
- **No Convex code per Mission type.** Adding a Mission type = editing the JSON manifest only. The dispatcher resolves contracts (review, blockers, External Job) from the matching `missionTypes[]` entry — there is no `switch (missionType)` anywhere in the backend. Logic specific to a Mission type lives in `AGENTS.md` (natural-language instructions read by the agent), not in application code.
- **Hidden Mission types**: an Agent can hide some of its Template's Mission types. This is a presentation choice made by the operator in OpenGroow, not a permission: the creation forms (Create Mission, Create Schedule) do not offer a hidden type and the Agent's workspace does not carry its instruction file. Everything else is unchanged — existing Missions and Schedules of a hidden type stay intact, readable and reviewable. It is a deny-list: by default nothing is hidden, and a Mission type added to the Template later appears on every Agent unless hidden. The Template declares nothing for it. It exists because a Template shared by several Projects can carry Mission types that only make sense for some of them (e.g. Video: a brand's formats on another brand's Project). _Avoid_: disabled (suggests the type is forbidden), permission.
- Review actions are **declarative** in the Template. OpenGroow executes them via a generic engine: it loads the Mission, checks permissions, resolves the Artifact, and calls the external service declared by the Template. Adding a Template must not require adding a specific business branch in Convex.
- A review action can declare the user inputs it needs (e.g. rejection feedback, publication date). Rejecting a deliverable is a generic relaunch of the Mission with human feedback, not an action specific to the Artifact type.
- The canonical review capabilities are `approve`, `reject`, and `publish`. They are optional and their UI label is configurable by the Template. `publish` exists only for deliverables that have a distinct publication step; otherwise `approve` can lead directly to `done`.
- Review uses a generic Template-driven rendering. The Template declares the content type to present (e.g. metadata, markdown, image, video) and the effects needed to load it; it does not reference a specific UI component.
- Review content is loaded via OpenGroow, not fetched directly by the UI from the external service. OpenGroow checks permissions, resolves the Template and the Artifact, then returns a safe representation of the content to display to the dashboard.
- The Activation/Reconfiguration and External Job review contracts use a declarative, bounded **external effect**: an HTTP call to a server declared by the Template, with interpolation of controlled references. OpenGroow interprets these effects; a Template does not contain arbitrary application code. Activation and Reconfiguration are therefore declared **as data** in the manifest (request body, extraction of the frozen identity from the response), just like review actions — Convex holds no service-specific knowledge (no SEO-specific or video-specific branch). A Template whose MCP owns its Project config end-to-end declares a `statusCheck` contract instead (an MCP tool call, see Config Completeness above) — same declarative-data model, different mechanism, still no per-service branch in Convex.
- The `AGENTS.md` file (uppercase) is the artifact read directly by the AI agent at execution time. `TOOLS.md` is retired (OpenClaw). Every declared Mission type has its own instruction file (`agentsMd` on `MissionType`) containing its workflow and tools, even when a Template has only one Mission type. Activation and refresh materialize every declared file at that same relative path in the workspace so it remains inspectable under Workspace Files — except the files of Mission types the Agent hides (see **Hidden Mission types**), which are not written and are removed from an already-materialized workspace. At dispatch, the dispatcher composes the base `AGENTS.md` with only the selected mission-specific file.
- **MCP servers are part of the Template's package**, just like its prompt, its commands, and its expected variables. An MCP server's config (transport, endpoint) is **embedded and versioned with the Template** — it is **not** a central infrastructure entity shared by OpenGroow. Changing a Template's MCP server means **publishing a new version of the Template**, never editing a global registry. (To be distinguished from the per-project access secret — e.g. `apiKey` — which lives on the Agent, not in the Template.)
- Examples: _SEO Writer_, _Hello_.

> **Creating a new Template (MCP)** — shortest path for a code agent:
> 1. Copy an existing Template package from a hub repository (`seo` for a review + publish deliverable, `video-demo` for a long External Job) and adapt `profiles/opengroow.yml` and `workspace/AGENTS.md`. Iterate with `pnpm template:link <folder> --project <projectId>` (it syncs on save): no Template content is compiled into OpenGroow (#674).
> 2. The manifest's **field contract** (`mcpServers`, `review`, `externalJobsByMissionType`, `actions`, `effect`, `requirements`) is typed in `packages/agent-templates/src/types.ts` — **source of truth**, read it instead of guessing.
> 3. `validateManifest` (`packages/agent-templates/src/index.ts`) enforces the contract and returns actionable error messages that serve as a checklist (e.g. every referenced `server` must be declared in `mcpServers`; a `doing` transition requires a `revision_run` effect; `kind ∈ {markdown,metadata,image,video}`).
> 4. Verify with `pnpm template:validate <folder>`; `npx vitest run packages/agent-templates` shows valid/invalid manifest shapes, and `fixtures/packages/` holds the packages the engine tests install.
>
> The _why_ of this declarative model (generic Artifact, review/External Job carried by the Template) is in **ADR-020** (`docs/adr/020-artifact-review-and-external-job-contracts-carried.md`).

### Tool

A program on the user's own machine (the paired Node host), called by an Agent through `exec` on that Node (e.g. `opengroow-android`), and distributed as an **npm package** installed next to OpenClaw. A Template declares the Tools it needs in `machinePrerequisites`: name, minimum version, the exact install command (`npm install -g …`) and the external programs npm does not cover (Python, `adb`). OpenGroow **displays** them (installation plan, Project "Prerequisites" section) and never installs them: it cannot know what is installed on the Node, so there is no installed/missing state.

- A **Plugin** is different: OpenClaw code loaded in the gateway of the Instance and shipped with an Agent (e.g. `report-sync`). Not to be confused with an **Official OpenClaw Plugin** (see `runtime.md`), which the operator enables on the Instance independently of any Template.
- _Avoid_: "plugin" for a machine Tool. (The "Android Plugin" below predates this term; it is a Tool.)
