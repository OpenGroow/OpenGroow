# Publishing

Part of the OpenGroow glossary: see [GLOSSARY.md](../../GLOSSARY.md) for the vision, bounded contexts and term index.

### Publisher

A Project-level integration that turns an approved deliverable into a post on an external service. A Publisher is one **adapter** (Postiz for social networks, GitHub for site repositories) plus its per-Project configuration (connection, the channels of the account added to it, service-specific settings per channel). It has its own page in the dashboard. Agents and Agent Templates never know which Publisher, adapter or channel id is behind a Publish target, and Templates do not name destinations at all.

- **Generic by design**: Postiz is only the first adapter; the concept is named after the role, not the tool.
- **Configured per Project**, not per Agent: one configuration serves every Agent of the Project, which removes the duplicated publishing config previously kept in each MCP.
- **Several per Project, at most one per adapter (ADR-075)**: a Project can have a Postiz Publisher and a GitHub Publisher side by side, each with its own connection and channels, each removable on its own. A channel key is unique across them, so the key alone says which Publisher a Publish target goes through.
- The Publisher publishes **only** on the human `publish` action of the review, or automatically with `autoPublish`. An Agent never publishes.
- _Avoid_: "Postiz config" (an adapter detail), "publishing MCP".

- **Publisher plugins (ADR-070)**: the service-specific part of the Publisher is a **Publisher plugin**, an isolated code module with a function contract (`testConnection`, `listChannels`, `publish`, `findPost`, `getStatus`) plus two data files (capabilities, channel options). Postiz is `packages/publisher/postiz` (hub), the contract is `packages/publisher-sdk`, it is an **installed Publisher package** downloaded from the hub (ADR-072): its data is stored at install (`apps/convex/publisher_packages.ts`) and its code is loaded only in Node actions (`apps/convex/publisher/load_node.ts`). The core keeps the Publication lifecycle described below. How to write one: `docs/PUBLISHER_PLUGINS.md`. Not an OpenClaw Plugin.

### Publish target

A destination a Publishable can be sent to: one **channel of one of the Project's Publishers** (an entry of the Publishers page, shown with its logo, name and @handle). Its key is always `<platform>:<handle>` (for example `instagram:love_youmake`, or `github:<owner>/<repo>` for a site repository, one channel per repository), with no exception: it is generated by the Publisher when the channel is added (a channel without a handle, or whose key is already taken by another channel of any of the Project's Publishers, is refused) and is the only publishing identifier in a Mission or Schedule payload (`payload.publishTargets`). The human chooses one or several channels when creating a Mission or a Schedule and can change them in the review; the Template does not declare them and an Agent does not choose them. There is no default. A key that is on none of the Project's Publishers is refused when the payload is saved; an unmapped one blocks `publish` (or makes the Publication `failed` under `autoPublish`) until the Publisher is fixed. Each target is sent through the Publisher that carries it.

- _Avoid_: "alias" or "target name" (the user never names it), "board id", "account".

### Publishable

The deliverable of a Mission expressed in the unified publishing format, of one **kind** from a closed set defined by OpenGroow (`video`, `image`, `carousel`, `article`). An `article` is a written page for a site (markdown body and cover, referenced by URL, plus its `slug`, `title`, `description` and optional `category`); it goes to a site's repository, not to a social network. A Publishable carries **references only** (media URLs, ids at the producing service), never content (ADR-010). The Agent Template's manifest declares, per Mission type, only the kind it produces.

- A new kind is added to the closed set by OpenGroow; it is not declared by a Template.
- **Declaration**: a Mission type declares `"publish": { "kind": "carousel" }` in its manifest entry, with optional `require` (optional fields the Template guarantees; can only tighten) `onPublished` (`{ server, method: "POST", path, body?, responseIndexingField? }`, the call made once per Publication reaching `published`; placeholders `{id}`, `{publication.externalUrl}`, `{publication.externalId}`) and `resource` (`{ tool, idArg?, map? }`, asynchronous MCP: the tool OpenGroow calls once when the External Job completes to get the media, merged into the Agent's text part). `media` is removed and rejected with a migration message. `validateManifest` checks them at Activation and rejects any other key (`targets` included). `require` is enforced on the RunResult (per-field error, the Agent retries) and listed in the Agent's `context.md`.
- **Fields (V1)**: `video` = `videoUrl`, `caption`, optional `coverUrl` / `title` / `link` / `tags`; `image` = `caption` and `imageUrl` or `variants`, optional `link` / `altText`; `carousel` = `caption` and ordered `slideUrls` or `variants`, optional `link` / `altText`; `article` = `markdownUrl`, `coverUrl`, `slug`, `title`, `description`, optional `category`. **Variants** (ADR-073) hold one set of media and text per service (`instagram`, `tiktok`…); the channel receives the variant of its service, else the default media. All accept a free `metadata` object. For an `article` the MCP owns the whole Publishable (ADR-074): `publish.resource` is required and returns all of it, and a `publishable` written by the Agent is rejected (a rule of the kind, not a manifest option). Otherwise the Agent returns it as `artifact.publishable` (required for `success` and `needs_human_review`, since both reach the review that publishes it); an invalid or missing one is rejected with per-field errors and the Agent retries.
- _Avoid_: "payload", "post".

### Publication

The tracked outcome of sending one Publishable to one Publish target: one Publication per (Mission, Publish target). It has a status (`pending`, `submitting`, `uncertain`, `scheduled`, `published`, `failed`), the external URL or id, the scheduled date and the error. A `failed` or `uncertain` Publication can be retried on its own. A Mission is `done` when all its Publications are `published` (`uncertain` blocks it). When the Mission type declares `publish.onPublished` (ADR-074), each Publication that becomes `published` calls it once (the Publication records the call, so a replay does not repeat it); a call that sends `{publication.externalUrl}` waits for the Publication to have its link. Its `responseIndexingField` is mirrored on `mission.indexing` (ADR-015); with several Publications the last answer wins. The call never blocks: on failure the Publication stays `published`, the Mission still reaches `done`, and the review shows "<Agent> was not notified" with a button to resend it (a call that never recorded its outcome is shown failed after 5 minutes).

- **Retry without duplicate posts**: the service has no idempotency key, so a retry must never blindly re-send. The Publication is `submitting` just before `POST /posts` (only one caller can claim it: the others are refused). A failure that does not prove the service rejected the request (network error, timeout, 5xx, unreadable answer) leaves it `uncertain` ("Postiz may have received this post; it will be checked before any new attempt"); only a clear 4xx rejection is `failed` (and drops the attempt window, nothing was created). Before re-sending an `uncertain` Publication (or a `failed` one that kept an attempt window and has no post id), the adapter's `findPost` lists the posts around the attempt and looks for one on the same channel with the same caption (HTML-stripped) created or dated within the attempt window; if found it is attached (`scheduled` or `published`) and nothing is sent; if the listing itself fails the Publication stays `uncertain` and nothing is sent; if not found it is sent once. The uploaded media ids (`media`, keyed by source URL) are kept on the row and reused by the retry. A `pending` or `submitting` row whose action died more than 5 minutes ago is retried through the same reconciliation.

- **Targets of a Mission**: `payload.publishTargets` (keys of Publisher channels, chosen at creation and editable on the Mission page while it is To validate or To publish, a read-only summary afterwards, no default). For a Mission type that declares `publish`, the review `publish` action is executed by the Publisher instead of an MCP effect.

- **Scheduled publication**: an optional `payload.publishAt` (epoch ms) on a Mission or a Schedule, editable on the Mission page while it is To validate or To publish. Without it the post goes out immediately; a date in the past is rejected ("publishAt must be in the future") by `missions.create`, `schedules.create`, `schedules.updatePayload` (unless the edit leaves an already-stale value untouched), `publications.setPublishAt` and the dashboard inputs; with it the adapter schedules the post and the Publication is `scheduled` with `scheduledAt`. A cron polls the adapter for scheduled Publications that reached their date (no webhook, like External Job polling) and moves them to `published` (or `failed`).

  - **A Publisher that cannot schedule** (manifest `scheduling: false`, the GitHub Publisher: a commit is immediate, ADR-074): a future `publishAt` on one of its channels is refused ("GitHub cannot schedule a post: remove the publication date") by `missions.create`, `schedules.create`, `schedules.updatePayload`, `publications.setPublishAt`, `publications.setTargets` (a dated Mission moved to its channel) and at publish time, before anything is sent. A date already past means "now" and passes.
  - **Caveat, recurring Schedule**: an absolute `publishAt` in a Schedule payload is copied as is to every Mission the Schedule creates. After that date every later Mission publishes immediately: spawning from a Schedule never fails on a stale `publishAt` (only creation/edit by a human is rejected), a past date at that point means "now". It is meant for one-off Schedules; there is no relative date ("tomorrow at 9") in V1.
  - The mutations that save a Mission or Schedule payload check that each `publishTargets` key exists on the Project's Publisher ("Unknown channel"). Mapping and the API key are checked when the Mission publishes: the human `publish` action is refused, and under `autoPublish` the Publication is `failed` with the error and the Mission stays `approved`.

- **Readiness**: `publish` is disabled on the Mission page, with the reason and a link to the Publishers page, when the Project has no Publisher, the Publisher has no API key, no channel is chosen ("Choose a channel"), or a channel of the Mission is unknown or not mapped (the reason names them). An Agent can be activated without any Publisher: publishing is only checked when publishing.

- **Do not confuse** with the Mission's `approved` status ("to publish"): `approved` is the human's validation of the deliverable; a Publication is what happens next.

### Postiz translation (V1)

- `image`, `video` and `carousel` all go through Postiz `upload-from-url` then `POST /posts`. A `carousel` uploads its slides **sequentially** (the upload order is the slide order) and sends them as the media list of one post; a `video` is a post with one media.
- Per-target settings (for example TikTok privacy) come from the Publisher config of the target (`settings` of the mapping), never from the Publishable (`metadata` is not forwarded). Optional Publishable fields are forwarded where Postiz supports them and ignored silently elsewhere: `link` (Pinterest destination), `altText` (image `alt`), `tags` (YouTube tags), `coverUrl` (YouTube thumbnail, uploaded like a media). Per-platform table: docs/TEMPLATE_DEVELOPMENT.md.
- **Several targets**: `payload.publishTargets` (set by the human, each a channel of the Publisher) makes one independent Publication per target. All are created `pending` up front; one failing does not stop the others. The `publish` action then fails, and replaying it redoes only the `failed` ones.

### Channel / kind capabilities

Whether a platform can carry a Publishable `kind` (`video`, `image`, `carousel`, `article`) is a property of the publishing service, so it is owned by the adapter, as **data**: `data/capabilities.json` of the Publisher package (Postiz: `packages/publisher/postiz` in the hub), stored with the installed package and read by the pure `capabilityIn(capabilities, service, kind)` (`packages/publisher-sdk`; no network, no per-platform branch, importable from Convex and the dashboard). It answers `supported`, `uncertain` or `unsupported`, with a human reason for the last two. An unknown adapter, platform or kind is `uncertain`.

- A package that predates a kind has no entry for it, so its channels are `uncertain` for that kind (allowed, with a warning) until the package is updated: Postiz declares `article: unsupported` from 1.0.6.

Data shape (`schemaVersion: 1`, validated by `parseCapabilities`):

```json
{ "schemaVersion": 1, "adapter": "postiz", "source": "<docs url>",
  "platforms": { "youtube": { "name": "YouTube", "video": "supported", "image": "unsupported", "carousel": "unsupported",
                              "reasons": { "image": "YouTube only takes a video" } } } }
```

Keys under `platforms` are the service's own platform identifiers (the channel's `channelService`). `unsupported` is set only when the service docs say so; anything not confirmed is `uncertain`.

- `unsupported` is **refused** server-side with a clear message ("YouTube cannot publish an image") by `missions.create`, `schedules.create`, `schedules.updatePayload`, `publications.setTargets` (kind from the Mission type's `publish` declaration) and at publish time (kind of the Publishable).
- `uncertain` is **allowed with a warning**.
- Dashboard: in the channel picker (Mission and Schedule creation/edit) and the review `Publication` section, `unsupported` channels are disabled with the reason; `uncertain` ones are selectable with a "Not confirmed" note.

### Large videos: runtime limits

**Local development exception:** Postiz only fetches public HTTPS URLs ending with `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` or `.mp4` (SSRF protection). For any other media URL (an MCP on `http://localhost`, a private host, a URL without extension such as `/videos/<id>/final`) the Postiz plugin downloads the media and sends its bytes to Postiz (`POST /upload`, multipart) instead. This is automatic, decided per URL (`postizCanFetch`), with no mode to configure. The file then lives in memory during the action, so it suits local-size videos; production MCPs should serve public HTTPS URLs so that Postiz fetches them itself.

The video is never downloaded by OpenGroow: the Convex action only sends Postiz the URL (`upload-from-url`), and Postiz fetches the bytes itself. A test pins this (the only `fetch` calls of an action are to the Postiz API). So the size of the video does not count against the action's memory nor its argument/return limits (16 MiB). What does count is the time of the action, which waits for Postiz to fetch and store the video: Convex actions are limited to 10 minutes, and a single `fetch` has no separate timeout inside that budget. A video whose upload to Postiz takes longer than that fails the Publication with an error (it can be retried). The size limit that actually applies is the one of Postiz and of the target network (for example TikTok, Instagram), not Convex's. These limits come from the Convex documentation and the call design; they were not measured against a live Postiz with a multi-GB file.

## Contract for MCP outputs

The **strict** contract is OpenGroow's: the Agent's `artifact.publishable`, validated per `kind` (`publish.require` can tighten it). The MCP output naming is a **recommended convention, not mandatory**: `videoUrl`, `coverUrl`, `imageUrl`, `slideUrls` (public HTTPS URLs reachable by Postiz), so the Agent copies fields 1:1. An MCP with another shape keeps working: the Agent translates (synchronous MCP), or `publish.resource.map` maps the names (asynchronous MCP). **Asynchronous MCP (produce, poll, fetch):** the Agent writes only the text part of the `publishable` in its `in_progress` RunResult (a media URL is rejected); when the External Job completes OpenGroow calls `publish.resource.tool` once with the job id, merges the media (the Agent's text always wins), validates the whole and moves the Mission to `needs_human_review`, or fails it with a per-field message and no partial `publishable`. The review of a Mission type that declares `publish` shows the media from the `publishable`, not from `review.path`. Who guarantees what: docs/TEMPLATE_DEVELOPMENT.md ("Contract at a glance").

## Postiz per-platform settings

Postiz requires platform-specific `settings` on each post (for example TikTok `privacy_level`, `content_posting_method`; Instagram `post_type`; Pinterest `board`). OpenGroow supplies working defaults itself (`src/settings.ts` of the Postiz package in the hub): the owner does not write JSON. TikTok defaults to a public `DIRECT_POST` (duet and stitch for videos, `autoAddMusic: "no"` on every post: Postiz refuses a TikTok post without it, a video included), Instagram to a feed post (a Reel is a single video posted as a feed post), and the Publishable `title` feeds TikTok, Pinterest and YouTube titles. The owner can override options per channel on the Publishers page (plugin data `data/channel-options.json` of the package, served to the dashboard through the registry): TikTok visibility (including `SELF_ONLY`), posting method (`DIRECT_POST` or `UPLOAD`, which sends the media to the TikTok app inbox), comments, duet, stitch; Instagram post type (feed post or story). The one required input is the Pinterest **Board ID**; a Pinterest channel without a board fails with an explicit message. A channel without options is not expandable. Stored values override the defaults. Source: https://docs.postiz.com/public-api/providers/. Field names come from those docs and are not yet checked against a live instance.

When Publish targets change during review, Publications for previous targets remain in the Mission's history. Completion depends on every currently chosen target having a published Publication; an old failed, uncertain or scheduled destination does not block its replacement. Removing the last unsuccessful target also completes an approved Mission when all remaining targets are already published.
