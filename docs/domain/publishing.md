# Publishing

Part of the OpenGroow glossary: see [GLOSSARY.md](../../GLOSSARY.md) for the vision, bounded contexts and term index.

### Publisher

A Project-level integration that turns an approved deliverable into a post on an external service. A Publisher is one **adapter** (V1: Postiz) plus its per-Project configuration (connection, the channels of the account added to it, service-specific settings per channel). It has its own page in the dashboard. Agents and Agent Templates never know which Publisher, adapter or channel id is behind a Publish target, and Templates do not name destinations at all.

- **Generic by design**: Postiz is only the first adapter; the concept is named after the role, not the tool.
- **Configured per Project**, not per Agent: one configuration serves every Agent of the Project, which removes the duplicated publishing config previously kept in each MCP.
- The Publisher publishes **only** on the human `publish` action of the review, or automatically with `autoPublish`. An Agent never publishes.
- _Avoid_: "Postiz config" (an adapter detail), "publishing MCP".

### Publish target

A destination a Publishable can be sent to: one **channel of the Project's Publisher** (an entry of the Publishers page, shown with its logo, name and @handle). Its key is always `<platform>:<handle>` (for example `instagram:love_youmake`), with no exception: it is generated by the Publisher when the channel is added (a channel without a handle, or whose key is already taken by another channel, is refused) and is the only publishing identifier in a Mission or Schedule payload (`payload.publishTargets`). The human chooses one or several channels when creating a Mission or a Schedule and can change them in the review; the Template does not declare them and an Agent does not choose them. There is no default. A key that is not on the Publisher is refused when the payload is saved; an unmapped one blocks `publish` (or makes the Publication `failed` under `autoPublish`) until the Publisher is fixed.

- _Avoid_: "alias" or "target name" (the user never names it), "board id", "account".

### Publishable

The deliverable of a Mission expressed in the unified publishing format, of one **kind** from a closed set defined by OpenGroow (V1: `video`, `image`, `carousel`). A Publishable carries **references only** (media URLs, ids at the producing service), never content (ADR-010). The Agent Template's manifest declares, per Mission type, only the kind it produces.

- A new kind is added to the closed set by OpenGroow; it is not declared by a Template.
- **Declaration**: a Mission type declares `"publish": { "kind": "carousel" }` in its manifest entry, with optional `require` (optional fields the Template guarantees; can only tighten) and `media` (media field to path in the MCP output, validated but not yet applied: OpenGroow has no place to read the output of a synchronous MCP call). `validateManifest` checks them at Activation and rejects any other key (`targets` included). `require` is enforced on the RunResult (per-field error, the Agent retries) and listed in the Agent's `context.md`.
- **Fields (V1)**: `video` = `videoUrl`, `caption`, optional `coverUrl` / `title` / `link` / `tags`; `image` = `imageUrl`, `caption`, optional `link` / `altText`; `carousel` = ordered `slideUrls`, `caption`, optional `link` / `altText`. All accept a free `metadata` object. The Agent returns it as `artifact.publishable` (required for `success` and `needs_human_review`, since both reach the review that publishes it); an invalid or missing one is rejected with per-field errors and the Agent retries.
- _Avoid_: "payload", "post".

### Publication

The tracked outcome of sending one Publishable to one Publish target: one Publication per (Mission, Publish target). It has a status (`pending`, `submitting`, `uncertain`, `scheduled`, `published`, `failed`), the external URL or id, the scheduled date and the error. A `failed` or `uncertain` Publication can be retried on its own. A Mission is `done` when all its Publications are `published` (`uncertain` blocks it).

- **Retry without duplicate posts**: the service has no idempotency key, so a retry must never blindly re-send. The Publication is `submitting` just before `POST /posts` (only one caller can claim it: the others are refused). A failure that does not prove the service rejected the request (network error, timeout, 5xx, unreadable answer) leaves it `uncertain` ("Postiz may have received this post; it will be checked before any new attempt"); only a clear 4xx rejection is `failed` (and drops the attempt window, nothing was created). Before re-sending an `uncertain` Publication (or a `failed` one that kept an attempt window and has no post id), the adapter's `findPost` lists the posts around the attempt and looks for one on the same channel with the same caption (HTML-stripped) created or dated within the attempt window; if found it is attached (`scheduled` or `published`) and nothing is sent; if the listing itself fails the Publication stays `uncertain` and nothing is sent; if not found it is sent once. The uploaded media ids (`media`, keyed by source URL) are kept on the row and reused by the retry. A `pending` or `submitting` row whose action died more than 5 minutes ago is retried through the same reconciliation.

- **Targets of a Mission**: `payload.publishTargets` (keys of Publisher channels, chosen at creation and editable in the review, no default). For a Mission type that declares `publish`, the review `publish` action is executed by the Publisher instead of an MCP effect.

- **Scheduled publication**: an optional `payload.publishAt` (epoch ms) on a Mission or a Schedule, editable in the review. Without it the post goes out immediately; a date in the past is rejected ("publishAt must be in the future") by `missions.create`, `schedules.create`, `schedules.updatePayload` (unless the edit leaves an already-stale value untouched), `publications.setPublishAt` and the dashboard inputs; with it the adapter schedules the post and the Publication is `scheduled` with `scheduledAt`. A cron polls the adapter for scheduled Publications that reached their date (no webhook, like External Job polling) and moves them to `published` (or `failed`).

  - **Caveat, recurring Schedule**: an absolute `publishAt` in a Schedule payload is copied as is to every Mission the Schedule creates. After that date every later Mission publishes immediately: spawning from a Schedule never fails on a stale `publishAt` (only creation/edit by a human is rejected), a past date at that point means "now". It is meant for one-off Schedules; there is no relative date ("tomorrow at 9") in V1.
  - The mutations that save a Mission or Schedule payload check that each `publishTargets` key exists on the Project's Publisher ("Unknown channel"). Mapping and the API key are checked when the Mission publishes: the human `publish` action is refused, and under `autoPublish` the Publication is `failed` with the error and the Mission stays `approved`.

- **Readiness**: `publish` is disabled in the review, with the reason and a link to the Publishers page, when the Project has no Publisher, the Publisher has no API key, no channel is chosen ("Choose a channel"), or a channel of the Mission is unknown or not mapped (the reason names them). An Agent can be activated without any Publisher: publishing is only checked when publishing.

- **Do not confuse** with the Mission's `approved` status ("to publish"): `approved` is the human's validation of the deliverable; a Publication is what happens next.

### Postiz translation (V1)

- `image`, `video` and `carousel` all go through Postiz `upload-from-url` then `POST /posts`. A `carousel` uploads its slides **sequentially** (the upload order is the slide order) and sends them as the media list of one post; a `video` is a post with one media.
- Per-target settings (for example TikTok privacy) come from the Publisher config of the target (`settings` of the mapping), never from the Publishable (`metadata` is not forwarded). Optional Publishable fields are forwarded where Postiz supports them and ignored silently elsewhere: `link` (Pinterest destination), `altText` (image `alt`), `tags` (YouTube tags), `coverUrl` (YouTube thumbnail, uploaded like a media). Per-platform table: docs/TEMPLATE_DEVELOPMENT.md.
- **Several targets**: `payload.publishTargets` (set by the human, each a channel of the Publisher) makes one independent Publication per target. All are created `pending` up front; one failing does not stop the others. The `publish` action then fails, and replaying it redoes only the `failed` ones.

### Large videos: runtime limits

The video is never downloaded by OpenGroow: the Convex action only sends Postiz the URL (`upload-from-url`), and Postiz fetches the bytes itself. A test pins this (the only `fetch` calls of an action are to the Postiz API). So the size of the video does not count against the action's memory nor its argument/return limits (16 MiB). What does count is the time of the action, which waits for Postiz to fetch and store the video: Convex actions are limited to 10 minutes, and a single `fetch` has no separate timeout inside that budget. A video whose upload to Postiz takes longer than that fails the Publication with an error (it can be retried). The size limit that actually applies is the one of Postiz and of the target network (for example TikTok, Instagram), not Convex's. These limits come from the Convex documentation and the call design; they were not measured against a live Postiz with a multi-GB file.

## Postiz per-platform settings

Postiz requires platform-specific `settings` on each post (for example TikTok `privacy_level`, `content_posting_method`; Instagram `post_type`; Pinterest `board`). OpenGroow supplies working defaults itself (`apps/convex/publisher/postiz_settings.ts`): the owner does not write JSON. TikTok defaults to a public `DIRECT_POST` (duet and stitch for videos, `autoAddMusic: "no"` for photos), Instagram to a feed post (a Reel is a single video posted as a feed post), and the Publishable `title` feeds TikTok, Pinterest and YouTube titles. The owner can override options per channel on the Publishers page (`apps/dashboard/src/components/channel-options.ts`): TikTok visibility (including `SELF_ONLY`), posting method (`DIRECT_POST` or `UPLOAD`, which sends the media to the TikTok app inbox), comments, duet, stitch; Instagram post type (feed post or story). The one required input is the Pinterest **Board ID**; a Pinterest channel without a board fails with an explicit message. A channel without options is not expandable. Stored values override the defaults. Source: https://docs.postiz.com/public-api/providers/. Field names come from those docs and are not yet checked against a live instance.
