# Projects, Agents and Providers

Part of the OpenGroow glossary: see [GLOSSARY.md](../../GLOSSARY.md) for the vision, bounded contexts and term index.

### Project

Business environment of a brand or business context. It is the user's primary workspace.

- A Project belongs to a **User**.
- A Project contains configured **Agents**, **Missions**, and **Resources**.
- From the user's point of view, a Project is the base organizational unit: _Acme Mobile_, _Acme Docs_, _Blog SEO_.
- **Do not confuse** with an Instance (infra concept). The Project is stable over time; the underlying Instance may be reprovisioned.
- **Persistence**: a `projects` table holds the Project (stable `_id`, `projectId`, `ownerId`, `displayName`, `settings`; ADR-066). `instances.projectId` links the runtime to it. `instanceId` stays the string key other tables store, deliberately not mass-renamed; the narrowing of the old shared row is a later release, and a data migration never ships in the same release as another one.

### Agent

AI entity configured within a Project, capable of executing Missions of a given type. The Agent is the customization of an **Agent Template** within the context of a Project.

- A Project holds **at most one Agent per Agent Template**. Two variants of the same Template's job (e.g. two blogs, two brands) belong in two Projects, not two Agents of one Project.
- An Agent is either `inactive`, `activating`, `active`, or in `error`.
- An `active` Agent can receive Missions.
- **Activation**: the process by which an Agent Template is copied into the Instance's workspace and made operational. Activation is asynchronous. For a Template whose external service owns its own Project configuration end-to-end, Activation is gated on **Config Completeness** (see below) instead of provisioning the resource itself.
- **Reconfiguration**: modification of the **configuration** of an already `active` Agent, without reactivating it or changing its Template. Not all Agents are reconfigurable — this is an **optional capability** of the Template (just as Activation may provision an external service). An Agent without editable configuration exposes no reconfiguration — this is the common case, not an exception: a Template whose only requirement is an immutable key (e.g. SEO Writer, Video) has nothing to reconfigure by construction. To change such a key, the user deactivates and reactivates the Agent with a new one. Reconfiguration never changes the Agent's `status`.
- **Frozen config vs reconfigurable config**: an Agent's configuration is split in two. The **frozen config** is set at **Activation** and can never change afterward because it defines the Agent's **identity** and the external resources it has provisioned. The **reconfigurable config** can evolve via Reconfiguration. **The Template is authoritative** on this split; the UI derives its read-only fields from it. Some Templates have no reconfigurable config at all (see Reconfiguration above).
- **Config Completeness**: for a Template whose external service (MCP) owns its Project configuration entirely — a human configures the Project directly on the MCP's own dashboard, and OpenGroow only holds the Project's access key — Activation cannot itself provision or verify that configuration. Instead, the Template declares a read-only **status-check** the MCP exposes (an MCP tool call), and OpenGroow asks it whether the Project is fully configured before letting the Agent reach `active`. The Agent stays `error` — with the MCP's own explanation and a link to its dashboard — for as long as the Project is incomplete or the key is rejected, closing the gap where an Agent looked `active` in OpenGroow but was silently guaranteed to fail on its first Mission. There is no periodic recheck once `active`: a Project broken after activation by editing it on the MCP's dashboard is a known, accepted gap.
- **Instagram account**: an Instagram login identity, identified by its handle, on whose behalf a Social Engagement Agent acts. Each Instagram account has its own engagement configuration and corresponds to a distinct Agent, even when several accounts share one Execution device. Account verification compares handles after trimming whitespace, removing an optional leading `@`, and ignoring case.
- **Visual Description**: bounded text (embedded text + scene) produced locally by a VLM from a crop of a post's media area, exposed as `postContext.visualDescription`. The screenshot itself is never sent anywhere; the Description is untrusted data (written by a stranger), consumed by the classifier and by the Agent drafting a comment. `null` when not requested, unconfigured, or failed.
- **Active Instagram account**: the Instagram account currently selected in the Instagram app on an Execution device. Before a Social Engagement Run acts, the Active Instagram account must match the Agent's Instagram account.
- **Available Instagram account**: an Instagram account already connected to Instagram and selectable on the Agent's Execution device. A Run cannot make an unavailable account available; if the account is absent or cannot be confirmed after selection, the Run stops before engaging with Instagram.
- **Instagram account verification**: the precondition that confirms the Active Instagram account matches the Agent's Instagram account before a Mission can engage with Instagram. If verification cannot establish that match, the Mission does not perform engagement actions.
- **Forum**: an external discussion site targeted by a Forum Engagement Agent. A Forum is a "managed site" scoped inside the Forum MCP (a generic, reusable MCP server declared by the Template), which holds its persistent state: Forum Threads and Forum Posts already seen or written, the Agent's Standing, and the Link Drop cooldown (see below). Each Forum corresponds to exactly one Agent and one Forum Account, mirroring the Instagram-account pattern above — never several Forums per Agent, never several Agents sharing one Forum.
- **Forum Account**: the login identity a Forum Engagement Agent uses on its Forum. Pre-created by a human (handle, credentials) and supplied to the Agent's config; the Agent never registers its own account. _Avoid_: confusing with the Instagram account — the two are parallel concepts for different Templates, not the same entity.
- **Forum Thread**: a discussion topic on a Forum, containing an ordered sequence of Forum Posts. The Agent reads a Thread's existing Posts to decide whether, and how, to reply.
- **Forum Post**: a single message the Forum Account writes on a Forum, in reply to a Forum Thread. A Forum Post is either a **Genuine Post** — ordinary participation, contributes to the Forum Account's Standing — or a **Link Drop**, the special-case Forum Post that contains a link to the Project's own service. A Forum Post is never both.
- **Standing**: a Forum Account's computed legitimacy on one Forum, derived by the Forum MCP from its Genuine Post history along two independent dimensions — **tenure** (elapsed time since its first Genuine Post) and **volume** (count of Genuine Posts accumulated since). Both dimensions must clear their configured threshold before a Link Drop is even offered as a possible action on that Forum; tenure alone would let a long-dormant account burst-post its way in, volume alone would let a brand-new account burst-post its way in. _Avoid_: confusing with the Link Drop cooldown below — Standing gates *first-ever* eligibility, the cooldown paces repeated Link Drops once eligible.
- **Link Drop**: the Forum Post where the Agent's own judgment has decided a Thread is topically relevant enough to place a link to the Project's own service. Unlike Instagram's `relevanceScore` (a judgment left entirely to the Agent), the Forum MCP enforces two **structural** gates the Agent's judgment cannot open on its own: the Forum Account's Standing must already clear its threshold, and a cooldown must have elapsed since its last Link Drop on that Forum. The Agent's judgment only ever decides relevance *within* an already-open gate — never whether the gate opens.
- From the user's point of view: _"My SEO Writer agent is active on the Acme project."_

### Provider

AI model route configured for a Project's Instance — either a linked OAuth subscription (e.g. ChatGPT/Codex) or a direct API key. A Provider's identity mirrors OpenClaw's own canonical provider id (`openai`, `anthropic`, `xiaomi`…) — see `docs/concepts/oauth.md` for why OAuth and API-key auth for the same backend share one provider id rather than being modeled as two providers.

- Exactly one configured Provider is **in use** at a time: the one `agents.defaults.model.primary` currently points at. All others are **configured** but idle.
- **Do not confuse with Agent's `active` status** — `active` is reserved for the Agent lifecycle (see Agent above). A Provider that isn't in use is never called "inactive"; it's "configured".
- Switching which Provider is in use never requires re-authorizing an already-linked subscription (a lightweight reactivation reuses the existing OAuth grant) — full re-authorization is only needed the first time a subscription is linked, or if OpenClaw reports the grant has expired.
- Two Providers can share the same underlying OpenClaw provider id (e.g. an `openai` API key and an `openai` subscription configured at once). Switching between *those two specifically* goes through OpenClaw's `auth.order.<provider>` mechanism instead of `model.primary` (both entries already resolve to the same provider id, so rewriting `model.primary` alone is a no-op) — see `activateAuthOrderProvider` in `apps/convex/auth_node.ts` and `handleAuthOrderActivate` in `control-socket-server.js` (#289).
