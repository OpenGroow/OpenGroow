# ADR-050: Run-level prompt snapshot for debugging — a read-only exception to ADR-018's no-persistence rule

**Status:** Accepted (amends [ADR-018](018-delivering-the-brand-core-via-run-context.md))

### Context

ADR-018 decided that `context.md` (Brand Core + Mission payload/`lastResult`/`lastIntermediateResult`) is rebuilt fresh at every dispatch and never persisted — deliberately, to get Brand Core edits "for free" on the next Run with no propagation mechanism. One accepted consequence was that nothing keeps a durable copy of what a given Run actually received; `context.md`, `run.md`, and the dispatched `AGENTS.md` exist only as files written into the Agent's workspace at dispatch time (`apps/convex/mission_dispatcher_node.ts`).

This becomes a real gap for prompt engineering. Improving a Template's output (e.g. `openmontage-agent`'s `create_reel`) depends on being able to inspect exactly what instructions and business context a specific past Run was given — including Runs whose workspace has since been reprovisioned or whose Brand Core has since been edited. Reconstructing this live (re-running `buildMissionContext` against current Convex state) would silently show today's Brand Core, not the one a past Run actually saw — misleading for debugging a specific Run's output.

Separately, the actually-most-impactful prompt for output quality is not `context.md` at all: it's the production prompt the Agent writes and sends to the Template's generative MCP tool (e.g. `generate_assets`'s `plan`, per-shot).

An earlier version of this ADR read this from `mission.lastIntermediateResult`/`run.intermediateResult` (ADR-026's job-polling mechanism), reasoning that openmontage-mcp's job output happens to echo back each asset's generation `prompt` in its `asset_manifest`. Live debugging surfaced two problems with that: (1) it's the job's *output* (generated file path, cost, echoed prompt) dressed up as if it were the *input* — never the literal argument shape `generate_assets` actually validates (`{shots: [{scene_id, type, prompt}], music: {prompt}}`, confirmed against openmontage-mcp's own source), and (2) whether the echo exists at all, and matches what was truly sent, is entirely up to each MCP's own choice to echo its input — nothing catches drift if it doesn't. For a debugging tool whose whole point is "is this exactly what was sent," an approximation that merely often agrees with the truth is the wrong contract.

### Decision

1. **`runs` gains two new snapshot fields, `agentsMdSnapshot` and `contextMdSnapshot`**, written once at dispatch time alongside the existing filesystem writes (`apps/convex/mission_dispatcher_node.ts`) — an immutable copy of exactly what that Run received, not a live pointer. This does not reopen ADR-018's propagation problem: it is a one-way, write-once audit trail per Run, not a second source of truth anything reads from or syncs against.
2. **The generative-MCP-call prompt is read live from the OpenClaw session transcript of the specific Run that made the call**, not from job output. The transcript (already exposed by `workspace_logs_node.getWorkspaceRunTranscript`, the mechanism behind "View logs") records every `tool_call`/`tool_result` turn the Agent makes, for every Template, with zero per-Template instrumentation — this is a generic capture point that already exists at exactly the right layer (the tool call itself), not something built for this feature. The dashboard's "Génération" panel filters that transcript for the `tool_call` turn whose `toolName` matches `generativeMcpCall`'s declared tool and renders its literal `arguments` — the exact payload sent, not an inference from the result.
   **Every Run has its own distinct session** (`sessionKey: \`mega-run-${runId}\``, `apps/convex/missions.ts`) — sessions are never shared across a Mission's Runs, unlike an earlier draft of this ADR assumed. The generative tool_call can therefore live on a Run *other than* the one the user opened "View prompt" from — e.g. an ADR-026 Intermediate External Job (`generate_assets`) resolves on one Run, and the Mission continues on a freshly dispatched Run that only calls a later, Terminal job (`render_video`), whose own session never mentions `generate_assets` at all. To find the right session, the dashboard first queries `runs.listByMission` for the Mission, then picks the Run whose own `intermediateResult.jobType` equals the declared tool name (the ADR-026 marker for "this Run is the one that resolved this specific job") and reads *that* Run's transcript — falling back to the currently-viewed Run's own transcript when no other Run matches (correct for Templates like `seo`/`video` where the generative call is a Terminal job with no resumption, so it's always the currently-viewed Run itself that made it).
   The transcript records a `tool_call` turn's name **prefixed by its MCP server** (e.g. `openmontage-mcp.generate_assets`, confirmed by inspecting a live session's `transcript_events` directly), while `generativeMcpCall` declares the bare tool name to stay consistent with `externalJobsByMissionType`'s job-type keys — the panel matches a `tool_call` whose name equals the declared tool name *or* ends with `.<toolName>`, rather than requiring an exact match.
   No new persistence is added for this: the transcript already survives indefinitely today (confirmed — no rotation/pruning/TTL code exists anywhere in this repo for session transcripts; ADR-025 already documents that Megaclaw deliberately never persists session data on the Convex side, reading it live on demand instead). The only residual risk — the underlying session storage being lost to an infrastructure event outside this repo (volume/container recreation) — is identical to the risk "View logs" already carries today, not a new one introduced here.
3. **A new optional manifest field, `generativeMcpCall: { toolName: string }`, declares per Mission type whether this panel should render at all**, and names which transcript `tool_call` to filter for. Declared for `openmontage-agent`/`create_reel`, `seo`/`create_article`, `video`'s mission types; left absent for `social-engagement`/`engage`, which has no generative MCP call. `validateManifest` cross-checks that the declared `toolName` matches an existing job-type key in `externalJobsByMissionType` for that Mission type (when one is declared), to catch a renamed job type stranding this pointer.

### Consequences

- `runs.agentsMdSnapshot`/`runs.contextMdSnapshot` duplicate content already written to the workspace filesystem, at Convex document size cost per Run — accepted, since this is a debugging surface, not a hot-path read.
- A Run's snapshot reflects the Brand Core/Template instructions *as they were at that Run's dispatch*, which will diverge from the live Brand Core/`AGENTS.md` over time — this is the point (historical accuracy for debugging), not a defect.
- The "Génération" panel now costs a live runtime round trip (same `RUNTIME_SESSION_TRANSCRIPT_READ` command "View logs" already dispatches) instead of a reactive Convex read — slower and depends on the runtime being reachable, versus the near-instant, always-available `run.intermediateResult` the earlier version used. Accepted: correctness (never showing the wrong payload) matters more than latency for a debugging surface used occasionally, not on a hot path.
- If a Template declares `generativeMcpCall` but the Agent never actually called that tool in the Run's session (e.g. it errored out before reaching that step), the panel shows "not found" rather than falling back to an approximate value — silence is preferred over a misleading echo.
- Editing a snapshotted prompt and re-dispatching a Run from it (prompt-iteration write path) is explicitly out of scope for this decision; it would need its own design (what layer becomes editable, and how an edited value re-enters `AGENTS.md`/`context.md`/a Mission's `payload` for a new Run).
