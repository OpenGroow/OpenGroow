# ADR-043: A SERP genuinely dominated by an unrelated entity is a terminal success, not a failure — and permanently excludes the Keyword

**Status:** Accepted (amends [ADR-026](026-intermediate-external-jobs-resume-the-mission-instead.md))

### Context

ADR-026 made `plan_article` an Intermediate External Job: when it comes back `blocked`, Megaclaw only resumes the Mission and hands the raw result to the Agent — the Agent itself judges the block and decides what to do next (revise, switch keyword, or give up). It left the "give up" branch underspecified: `AGENTS.md` grouped three non-retryable `reason` values (`unsupported_content_type`, `out_of_scope`, `ambiguous_intent`) under a single instruction — write `failed` or `needs_human_review`, agent's choice.

In practice, this produced a wrong outcome for `ambiguous_intent`: a keyword like `love of a lifetime` (or `best practices`, which coincidentally collided with a song of the same name) whose SERP is entirely monopolized by an unrelated non-editorial entity (a 1990s rock song, in both observed cases) got reported as `failed` — a Mission-level error — even though nothing malfunctioned. seo-mcp's own SERP-arbiter prompt (`src/prompts/serp-arbiter.md`) already distinguishes this case carefully: it instructs the arbiter LLM not to give up just because a SERP is mixed or ambiguous (rule 1 — "ambiguous or mixed SERPs often require a pillar-hub page"), and only to set `skip: true` when the query is "clearly out of scope, unsafe, or has no editorial value." So by the time `ambiguous_intent` reaches Megaclaw, the arbiter has already considered and rejected the pillar-hub alternative — there is no viable editorial angle left to try, with or without SERP grounding. Writing the article anyway, ungrounded, would only produce content the system's own arbiter has already judged worthless.

`GLOSSARY.md`'s RunResult table defines `failed` narrowly: "the Agent has encountered an unrecoverable error." A SERP being genuinely, correctly judged unusable is not an error — it is the same shape as the template's existing `no_new_articles` case (`internal_linking` mission type), which already routes to `success` for an analogous "nothing to do, and that's fine" outcome.

Separately, nothing durable happened on a `blocked`/`ambiguous_intent` outcome: the Keyword stayed `candidate` in seo-mcp, so a later Mission could pick the exact same keyword and hit the exact same wall again. seo-mcp already has a permanent Keyword exclusion mechanism (`status: "excluded"`, `excludedReason`), used today by both a human (triage page) and a machine (`discover_keyword_opportunities`'s automatic rejections) — but nothing wired it to `plan_article`'s own blocking outcome.

A third gap surfaced once the auto-exclusion above was in place: a Project running `create_article` on a daily Schedule with `autoPublish` expects roughly one article per day. Ending the Mission at the very first `ambiguous_intent`/`out_of_scope` verdict — even as a non-error `success` — still means that day produces no article, even though `list_keywords` may hold several other, perfectly viable candidates. `schedules.tick` (`apps/convex/schedules.ts`) does not special-case a Mission's outcome — it creates a new Mission at the next scheduled slot regardless of the previous one's status — so the daily cadence does recover *tomorrow*, on a fresh Mission with the excluded Keyword no longer offered. But that still costs today's article, for no reason: `list_keywords` was never actually exhausted, only the one Keyword picked first.

### Decision

1. **Switch keyword within the same Mission before giving up.** `ambiguous_intent` and `out_of_scope` — both genuine "no viable editorial angle" verdicts from the SERP arbiter, for *that one Keyword* — no longer end the Mission on the first hit. The Agent calls `list_keywords` again (the just-excluded Keyword no longer appears) and retries `plan_article` with the next-highest-priority candidate, looping through this way until either a plan succeeds or `list_keywords` has no candidate left to offer. Only then is a **terminal `success` RunResult** written (Mission `done`), with `summary` listing every Keyword auto-excluded for `poor_serp` during the Mission. This is deliberately uncapped (exhaust the full list, not a fixed attempt count) — consistent with ADR-026's existing revision loop, which is also uncapped by default. `unsupported_content_type` stays on the original `failed`/`needs_human_review` instruction — it signals a configuration/input mismatch, not an editorial dead end, and switching keyword would not fix it.
2. **No new RunResult or Mission status.** `success`/`done` without an Artifact is already a valid, existing shape (`RunResult.artifact` is optional; the `no_new_articles` case already produces it) — reusing it keeps the vocabulary in `GLOSSARY.md` accurate instead of adding a status whose only benefit is cosmetic.
3. **`blocked_external` was considered and rejected** for this case: that Mission status means "exits only via manual retry," i.e. something is genuinely stuck pending outside action. Here, seo-mcp has already resolved the situation on its own (auto-exclusion) by the time the Mission ends — nothing is pending. A human disagreeing with the auto-exclusion is an optional follow-up (restoring the Keyword on seo-mcp's dashboard for a future run), not a blocker on this Mission.
4. **seo-mcp auto-excludes the Keyword** as a side effect of `plan_article` blocking with `ambiguous_intent`/`out_of_scope`: a new machine Exclusion Reason, `poor_serp`, is added alongside the existing ones (`insufficient_search_volume`, `no_topical_overlap`, `llm_rejected`). Unlike those three (written by `discover_keyword_opportunities` before a Keyword is ever offered), `poor_serp` is written by `plan_article` after the Keyword was already offered and picked — a new pipeline entry point into the same Exclusion Reason vocabulary. The wire contract of `plan_article`/`get_plan_status` (`status: "blocked"`, `reason` enum) is unchanged; only a DB side effect is added. A human can always restore the Keyword from seo-mcp's triage page, same as any other exclusion.
5. **No agent-side override.** Consistent with ADR-026's rejection of Agent-side negotiation over an External Job's verdict, the Megaclaw Agent has no mechanism to contest `ambiguous_intent`/`out_of_scope` within the Mission — it accepts the verdict and reports it. Disagreement is resolved out-of-band by a human on seo-mcp's dashboard, exactly like any other Keyword exclusion.
6. **No new notification mechanism.** Megaclaw has none today (no email/webhook — confirmed absent repo-wide); a `success` Mission with an explicit `summary` surfaces passively on the kanban board like any other Mission. Proactive notification of Mission outcomes remains a separate, unscoped product concern.

**Rejected alternative: a Convex-level same-day Mission retry.** Considered creating a fresh Mission immediately (instead of waiting for the next Schedule tick) whenever a `create_article` Mission ends `success` without an Artifact. Rejected because it re-implements, in Convex, a capability the Agent already has under ADR-026 ("switch keyword" is an explicitly named option) — and because it would need its own Mission-type-specific trigger and retry cap in Convex, violating the existing "no per-Mission-type branching in Convex" principle (ADR-026's consequences). Keeping the loop entirely on the Agent side, inside the same Mission, needs no new Convex mechanism and no cap logic beyond "no candidates left."

### Consequences

- `packages/agent-templates/templates/seo/AGENTS.md`: Step 4 (`list_keywords`) is re-entered from Step 5 on a `poor_serp` block instead of ending the Mission, always picking the next highest-priority candidate (ignoring the payload's `keyword` hint on re-entry); Step 5's non-retryable branch is split in two — `ambiguous_intent`/`out_of_scope` → switch keyword, terminal `success` only once `list_keywords` is exhausted; `unsupported_content_type` → `failed`/`needs_human_review` (unchanged).
- `seo-mcp`: `machineExclusionReasonSchema` (`src/tools/keywords.ts`) gains `poor_serp`; `article-planning.ts` calls a new session-less `excludeKeywordAutomatically(keywordId, reason)` helper when `planBlockedReasonFromSerp()` returns `ambiguous_intent` or `out_of_scope`; the dashboard's exhaustive `EXCLUSION_REASON_LABELS` map gains the corresponding label, enforced by TypeScript.
- `serp_unavailable` is unaffected — it stays retryable, never excludes the Keyword, and is unrelated to this decision (a temporary SERP-fetch failure is not the same fact as a SERP that was fetched and found permanently unusable).
- If a future case shows the Agent needs a way to flag disagreement with the arbiter's verdict without blocking the Mission, that can be added to the `success` `summary` text — no schema change implied.
