# ADR-091: Production Recipes are mandatory for creative Missions, and Templates bundle them

**Status:** Accepted. Amends ADR-083 ("never selected automatically", the `production-recipe` provider) and ADR-090 ("deleting a recipe is never refused").

## Context

A Mission of any Mission type can be created without a Production Recipe: from the Create Mission form ("No recipe"), from "Run now", and from a Schedule tick, which cannot even carry one. The Publications of those Missions are unattributed. Nothing says which Mission types produce content, so the server could not require a recipe even if it wanted to. And a recipe exists only if the user wrote one, so a user who wants plain content has no easy path.

## Decision

- **A Mission type declares `kind: creative | operational`.** It is explicit and independent of `publish`: a creative Mission type may produce content that is not published or planned. Every Mission type of a Template declares it; there is no third value and no default. A Template without Mission types stays valid.
- **The new contract is profile `schemaVersion: 2`**, for every Template (Strategy and Source included). A stored version with an older `schemaVersion` is **outdated**, derived and never stored. It stays readable from its stored manifest, so Missions, Runs, Artifacts, Publications and Recipe Snapshots keep their history, and approving and publishing existing content still works. No new Run starts from it until the Project updates the Template: Mission creation and the new Runs of an existing Mission (retry, revision, resume), Job Runs and Recipe Generation are refused at the point where the Run is inserted. Runs already inserted run to the end. A Mission keeps its pinned Template version: a Mission pinned to an outdated version can start no new Run (retry, revision, resume) even after the Project updates the Template, a resume refused for that reason ends the Mission as failed with an explicit message and its history kept, and no Mission is ever migrated to another Template version. A Schedule whose Template is outdated skips its occurrences without an error and resumes after the update without any change to its status. No validator or dispatcher runs an old contract.
- **A creative Mission type bundles its recipes.** The manifest lists `recipes: [{ id, path, default }]`, files under `recipes/` at the package root, exactly one `default: true`. A Bundled Recipe is a normal Production Recipe row (same versions, same snapshot) identified by Project, Template, Mission type and its manifest `id`.
- **Bundled Recipes are protected.** They cannot be edited, retargeted or deleted on their own, and are duplicated into independent Custom Recipes (no inheritance). A recipe belongs to the Project, not to an Agent: deleting an Agent keeps every Bundled and Custom Recipe, with its target, unusable until a compatible Agent exists, and reinstalling the Template reuses them. Only deleting the Project removes them. This amends ADR-090 for Bundled Recipes only; Custom Recipes keep its rules.
- **Provisioning is idempotent and separate from validation.** One function provisions the recipes of a Template: on install and link, on applying an update, on Agent activation, and by a backfill. It adds a Recipe Version only when the content changed. Creating a Mission never creates a recipe.
- **A recipe removed from a Template version becomes a Custom Recipe.** It keeps its identity, versions, snapshots and references and loses its Bundled and Default marks. A Custom Recipe is never overwritten: a Bundled Recipe that comes back is provisioned as a new row.
- **The server requires an explicit, compatible recipe for every creative Mission**, in the one function that inserts Missions. Compatibility is: same Project, same Template and Mission type, and the type is creative in the pinned Template version. The server never picks one. The interface preselects the Default Recipe, the Strategy Agent picks explicitly. A Mission of an operational type is unchanged.
- **The recipe context is native for creative Missions.** The snapshot is always taken and rendered; the `production-recipe` provider declaration is no longer needed. The name stays accepted by the manifest reader so stored versions remain readable.
- **A Schedule of a creative Mission type carries its `recipeId`**, used by the tick and by "Run now" through the same validation as the Create Mission form. Default Schedules record the Default Recipe. When a recipe is deleted or stops being compatible, its Schedules are paused with `pausedReason: "recipe unavailable"`, listed before a deletion, and refused on resume until a compatible recipe is chosen. The Default Recipe never replaces it silently. Existing Schedules are backfilled with their Default when the Project applies the Template version that provides it.
- **Attribution is unchanged** (ADR-084): it is read from the Mission's snapshot, which every creative Mission now has. No `recipeId` is added to Publications. "Unattributed" only describes historical Publications and those of operational Missions.
- **Vocabulary.** `contentType` replaces the `kind` that `list_mission_types` and `list_production_recipes` returned for `publish.kind`, renamed at once in every consumer and in the Strategy prompts, with no alias and no double field. The stored Content Planning fields follow: `productionTargets[].contentType` (Job config), `contentPlanning.targets[].contentType` (the pin on a Run) and `plannedContents.contentType`, moved from `kind` by the migrations `renameProductionTargetsKindOnJobs`, `renameContentPlanningKindOnRuns` and `renamePlannedContentKind`; the dashboard reads and Convex views expose `contentType` too. The Template id and Mission type of a recipe are its **Recipe target** (`RecipeTarget`, `setTarget`, unchanged); a **Production target** stays the quantity Content Planning aims for and a **Publish target** a destination. `kind` therefore only means creative or operational. `format` and `layout` are kept for the composition of a content and are not used here.
- **Historical data is never rewritten**: Missions, Runs, Publications and Recipe Snapshots.

## Consequences

- Rollout is coordinated across the three repositories, and the Template update is mandatory: the manifest readers refuse unknown keys, so the order is the product reader, a new `groowhub-cli`, the CLI pin in both hub repositories, the Template versions, then the enforcement. The Template releases are prepared first and cannot be applied by an older deployment, which refuses the new `schemaVersion`; the deployment that carries the new reader, the blocking, the enforcement and the MCP rename is a single one. Details in the PRD.
- A creative Mission type with no `publish` has no Content Type and cannot be planned; that is accepted, not solved here.
- "No recipe" disappears from the interface and the code that supported a recipeless creative Mission is deleted.
- Out of scope: the creative structure of recipes, Fixed/Guided/Automatic parameters, Production Skills, the Recipe Compiler, the Production Manifest, a generic video MCP, Recipe Testing, distribution through the hub marketplace, and creating a Mission from a Planned Content.
