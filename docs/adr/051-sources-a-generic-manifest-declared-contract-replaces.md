# ADR-051: Sources — a generic, manifest-declared contract replaces Observation; a SourceJob (not a Mission) normalizes and enriches

**Status:** Accepted

### Context

Observations (ADR-044 to 049) were built for one origin: social posts harvested by `social-engagement`. Their shape (`platform`, `sourceAccount`, `postUrl`, engagement counts, `creativeFeatures`), their enrichment (`enrich_observations`), their scoring and their production planning are all social-specific, and `enrich_observations`, `score_observation` and `plan_observation_production` are Mission types although no human ever asks for them. The product needs other origins (a keyword provider, product analytics) to land on the same page and be comparable, without Convex or the dashboard learning anything about each service.

### Options considered

- **Agents write their own labels, types and analysis layout on every record** — rejected: a weak model writes "Instagramm" one day and "instagram" the next, and the dashboard needs per-origin renderers, which breaks the "no per-service code" rule (ADR-020).
- **A closed vocabulary (enums) for the common marketing layer** — rejected: an enum written up front must cover social, SEO and product signals and will be wrong for the next origin. The comparable layer is the score, which Megaclaw computes; the common layer only describes.
- **Normalize inside each Mission's own Run** — rejected: it puts the schema in the context of Agents whose context is already full (`engage`), forces a whole Mission to be redone when normalization fails, and hides normalization from any retry surface.
- **A Mission-end trigger for normalization, or a `from`/`produces` field linking Missions to Sources** — rejected: it makes Missions (human, business-facing) aware of Sources and requires a Template-level field just to say where a report lives.
- **Per-Run "ingested" marker on `runs`** — rejected: meaningless for origins that do not read Runs (a keyword provider), and would touch the Runs of Templates unrelated to Sources.
- **Extending `Schedule` to also target SourceJobs** — rejected: `Schedule`'s Mission-specific fields (`type`, `payload`, `autoPublish`, `lastMissionId`) would become optional on half the rows.

### Decision

**A Source replaces the Observation.** One dated, append-only record with three layers: common metadata, a common marketing representation (free-text, bounded — the fields and their types matter, not the wording), and an origin-specific analysis. Scoring is never written by an Agent; Megaclaw computes it, with the same rules for every origin (deferred — out of scope here).

**Everything an origin needs is declared in the Template manifest, at Template level, in `sources[]`** — a hybrid that mirrors `missionTypes[]`: each declaration carries `type` (the Source type, unique in the Template; it is the `sourceId` value an Agent writes), `label`, a free-text `family` (such as `social-video`), an `agentsMd` instruction file (same field name as `missionTypes[].agentsMd`) and an `analysisSchema` JSON Schema. Asynchronous enrichment is declared next to it in `externalJobsBySource`, keyed by Source type, at Template level exactly like `externalJobsByMissionType` (the polling core, without the Mission-only completion fields). `validateManifest` checks all of it at Activation: every `agentsMd` of the Template (Mission types and Sources) must be unique, and `analysisSchema` may only use a strict allow-list of JSON Schema keywords that both the validator and the dashboard rendering support: `type`, `properties`, `required`, `items` (single schema, no tuple), `enum`, `format`, `minimum`/`maximum`/`exclusiveMinimum`/`exclusiveMaximum`, `minLength`/`maxLength`, `minItems`/`maxItems`, `pattern`, `additionalProperties` (boolean), `title`, `description`, `default`, `const`. Any other keyword (`allOf`/`anyOf`/`oneOf`/`not`, `if`/`then`/`else`, `$ref`, `patternProperties`, ...) is rejected with its path; Convex enforces the same schema on every write. `missionTypes[]` is unchanged: a Mission knows nothing about Sources.

**A SourceJob — not a Mission — does the work.** A Mission is triggered by a human and may be reviewed; filling the database is neither. One SourceJob per Agent is scheduled by the user from a Jobs page (its own table, separate from `schedules`, which only ever create Missions). Each tick it receives the Runs **of Missions** of the Agent completed since a cursor kept on the job side (a SourceJob's own executions have no Mission, so they are never part of its batch by construction; the batch query must start from Missions rather than "all Runs of the Agent"), reads whatever its Source's `.md` says to read (a Run's `report.json`, or a call to an MCP for a polled origin), normalizes into the common schema and writes through an HMAC route with the validation errors returned to the Agent. Enrichment is a phase of the same SourceJob: it hands off a long-running external job, Megaclaw polls it, and the same SourceJob resumes with the result. The common schema is defined once (zod) and derived into the JSON Schema injected into the Agent's context, the route validator and the table validator.

**The `sourceJobs` table.** One row per Agent (owner, instance, template; unique per Agent) holding: `state` (`active` / `paused`), the recurrence (same fields as `schedules`: unit, day of week or month, hour, minute, timezone), `nextRunAt`, the cursor (`cursorAt`), `lastRunAt`, `lastOutcome` (`succeeded` / `failed` / `skipped`), `lastError` and `inFlightRunId`. It replaces the separate scheduling table sketched above: recurrence and cursor describe the same object, since there is one SourceJob per Agent. It depends on no Mission's Runs, so it serves polled origins (an empty batch, the cursor advancing harmlessly) exactly as it serves origins fed by Runs.

**Executions live in `runs`, with the Mission link made optional.** The handoff, polling (`awaiting_job`) and resumption (`resumed`) machinery is built on `runs`; enrichment reuses it as is. Every tick creates one execution Run without a Mission, for every Agent whatever its origins.

**Lifecycle.** The row is created at Activation of an Agent whose Template declares Sources: `active`, daily by default (which preserves today's automatic behavior), cursor at creation. A dedicated cron picks rows that are `active` and due. If an execution is in flight (`running` or `awaiting_job`) the tick is skipped and `nextRunAt` advances; otherwise Megaclaw builds the batch — the Runs of Missions of the Agent with `completedAt` after the cursor and up to a bound fixed at build time, plus Sources flagged for retry — creates the execution and dispatches it. There is no "empty batch" guard. On success the cursor advances to the bound; on failure it does not and `lastError` is set. During an asynchronous enrichment the row stays in flight and later ticks are skipped; the job succeeds when a resumed execution ends without a further handoff. A manual retry puts the Source back to `processing`, flagged, and it joins the next batch (no "run now" in V1). Deactivating an Agent pauses its row (cursor kept, so Runs of the inactive period are picked up on reactivation); deleting it deletes the row, Sources remain.

**Cutover and cleanup.** The old harvest at Run end and the enrichment dispatch chain are replaced, not run alongside: with no deduplication, both writing would duplicate every post. Until then the new path is inert behind a single deployment-level switch (off by default), which the cutover turns on while turning the old harvest and enrichment dispatch off. The switch is a single deployment that disables both, migrates `observations` to `sources` and creates the `sourceJobs` rows with the cursor at the switch time (Runs completed before were already harvested; Runs completed after are in the batch). In-flight enrichments are **drained** first: new `enrich_observations` Missions are frozen, in-flight ones finish, then the switch happens (rows still `pending` are picked up by the SourceJob) — redoing them would bill the user's own model key twice. Dead code is removed only after the new path is verified live: the harvest call at Run terminal state, the debounced enrichment dispatch and its one-active-Mission rule, the application of the enrichment result and its `enrichmentStatus` transitions, the `enrich_observations` Mission type (instruction file, manifest entry, external-job contract, context provider, Mission-list exclusions and Run special-cases), the `observation_deep_analysis` Artifact kind, the tests covering them and the regenerated embedded template content. The daily scoring cron and selection are untouched.

**Final state (issue #537).** The cleanup is done and the switch, its freeze companion and the cutover tooling (`cutover.ts`, `observations_to_sources.ts`, the runbook) are gone: the SourceJob path is the only path. Removed: the harvest at Run terminal state (`observations.insertMany`, `observations_node.ts`, the report reader), the enrichment dispatch and the application of its result (`observations_enrichment.ts`), the `enrich_observations` Mission type (instruction file, manifest entry, its `externalJobsByMissionType` contract, the Mission-list exclusion, the shared-node special case in `runs.ts`), the `observation_deep_analysis` Artifact kind (from the manifest types and the RunResult zod contract), the Observations pages and their tests, and the regenerated embedded template content. The daily scoring cron and selection are untouched and read Sources (they have nothing scored to select while scoring is dormant, see below). Decisions taken with it:

- **The `observations` table is purged, unconditionally and irreversibly.** The `purgeObservations` migration (registered in `PENDING_MIGRATIONS`, run by `runAll` after the deploy) deletes every row, batched and idempotent, with no condition. The table cannot leave `schema.ts` in the same deploy: `migrations.define` types its `table` against the schema, so the table stays declared with a permissive validator (`v.any()`) and no application code touching it, and a follow-up release removes the declaration once the purge has run everywhere. It is a deliberate gap with "drop the table from the schema". `observations_to_sources.migrate` must have run and been verified before this ships (deployment in two steps: ship the cutover, run its runbook, only then ship this), because the purge cannot be undone. `sources.legacyObservationId` stays as a plain string so migrated rows keep validating, and `missions.sourceObservationId` now only accepts a Source id (the migration had already re-pointed every production Mission).
- **`enrich_observations` Missions are deleted by migration.** `deleteEnrichObservationsMissions` deletes those Missions with their Runs and the Runs' reconcile events (the only rows hanging off a Mission: `runs.by_mission`, `runReconcileEvents.by_run_created`); other Missions and Mission-less Runs are untouched. The sibling `cleanEnrichObservationsSchedules` (registered right after it) deletes the `schedules` of type `enrich_observations` (nothing else hangs off a Schedule, and they would keep creating Missions of a type that left the manifest) and resets `lastMissionId` to undefined on the remaining Schedules when it points to a Mission that no longer exists. The dashboard derives the creatable types from the manifest, so no UI offers this type any more.
- **The Convex `artifactV` validator keeps the `observation_deep_analysis` literal**, flagged legacy, so a schema push still validates any surviving document carrying it. Nothing writes it any more.
- **Scoring is dormant.** The `score_observation` Mission was dispatched at the end of the old enrichment result application; nothing dispatches it on the SourceJob path (a dispatch added to `sources.complete` was removed again: scoring is a separate piece of work). `score_observation` and `plan_observation_production` (Mission types, instruction files, the Source read) are kept as they are, but no Source is scored or selected until that work is done.
- **Provenance and raw capture on the Source.** A Source written through `POST /api/sources` carries `runId` and `sourceJobId`, set server side from the SourceJob execution in flight (never accepted in the payload), plus an optional verbatim `raw` (64 KB cap). `rawData` (the report.json of a migrated Observation) is a distinct read-only legacy column; `runId` is one field shared with the Run reference of migrated rows.

**Migration.** `observations` becomes `sources` in place, existing rows becoming `instagram-reel` / `tiktok-post` Sources; scoring, selection and planning keep their behavior on the same rows, their fields flagged as legacy until they are lifted out.

### Consequences

- A new origin is a manifest entry plus an instruction file — no Convex or dashboard change; the dashboard renders `analysis` generically from its declared schema.
- SourceJob retries after a partial failure can duplicate Sources (no deduplication in V1); a natural key linking a series is the intended fix, and also the way to relate a keyword collected weekly.
- A SourceJob costs an Agent session even when nothing new exists; the cost is bounded by the cadence the user chooses. There is deliberately no mechanical skip in V1.
- A Source appears at the next SourceJob tick, not right after the Mission that produced its raw material.
- **Cursor on `runs.completedAt` (verified).** The four terminal Run transitions (`completed`, `resumed`, `failed`, `cancelled`, all in `runs.ts`) each set `completedAt`, and no other code path writes a Run's status — so no backfill is needed for new Runs. The cursor must include all four statuses, not just `completed`: a failed or cancelled `engage` session still leaves a partial `report.json` worth normalizing. The `runs` table has **no index** on `completedAt` yet (one on `["instanceId", "templateId", "completedAt"]` or equivalent must be added). Runs older than the first SourceJob are not backfilled: the first cursor starts at the SourceJob's creation.
- **JSON Schema validation (verified).** `apps/convex` pins `zod ^3.25.76`, whose `zod/v4` subpath has `toJSONSchema` but **no `fromJSONSchema`**. `zod@4.4.3` (already in the pnpm store, used by other packages) has `fromJSONSchema`, builds schema objects with **no `Function` use**, and its parser only enables code generation behind an `allowsEval()` probe that falls back safely where `new Function` is refused. Adopting it means upgrading `zod` in `apps/convex` to `^4`, which changes the root `"zod"` import used by `run_result.ts`, `indexing.ts` and `workspace_logs_node.ts` (written for v3): they must move to `zod/v3` or be migrated. `ajv` is present only transitively and generates code at runtime, so it is not a candidate. **Verified in the real Convex runtime (issue #526): it works.** `apps/convex` now runs on `zod ^4.4.3` (the three modules were migrated to v4, RunResult error messages unchanged). A one-off Convex function deployed to a real local Convex backend (the Rust backend's V8 runtime, not `edge-runtime` under `convex-test`) called `z.fromJSONSchema` on a representative schema (nested objects, array of objects, `format: uri`, `enum`, `minLength`/`maxLength`, `minimum`/`maximum`, `maxItems`, `required`) and `safeParse`d a valid and an invalid payload: the valid one passed and the invalid one returned all seven violations (nested paths included). No fallback interpreter is needed. The keyword subset is pinned by `apps/convex/test/json_schema_validation.test.ts`. Caveat: the check ran on a local backend, not on Convex Cloud.
- **Supported keyword subset is bounded by `fromJSONSchema`.** It supports `type`, `enum`, `const`, `properties`, `required`, `items`, `minItems`/`maxItems`, `minLength`/`maxLength`, `pattern`, `format` (including `uri`), `minimum`/`maximum`, `oneOf`/`anyOf`/`allOf`; and throws on external `$ref`, `not`, `if/then/else`, `dependentSchemas`, `unevaluatedProperties`/`unevaluatedItems`. `validateManifest` refuses the same set at Activation, so a manifest can never declare a schema Convex cannot enforce (and the earlier "restricted subset" can simply be "what `fromJSONSchema` accepts", minus `$ref`).
- **One zod definition, three derivations (verified).** `convex-helpers@0.1.119` ships `zodToConvex` for both zod 3 (`zod3.ts`) and zod 4 (`zod4.ts`) with peer range `zod ^3.25 || ^4`, so the common layers can be defined once and derived into the table validator regardless of the zod upgrade; `z.toJSONSchema` covers the schema injected into the Agent's context.
- The `Observation` glossary entry is now a pointer to Source (issue #537); the daily scoring/planning path remains and reads Sources. ADRs 044–049 are historical and are not amended.
